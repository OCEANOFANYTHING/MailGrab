# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MailGrab is a single-file Python CLI tool ([MailGrab.py](MailGrab.py)) that crawls a website (BFS over `<a>` links, same-origin-ish path resolution) and regex-extracts email addresses from the fetched HTML. There is no package structure and no linter/formatter config — the crawler itself is one script plus an installer. A second file, [mailgrab_mcp_server.py](mailgrab_mcp_server.py), exposes the same capability as an MCP (Model Context Protocol) tool so AI coding agents can call it directly — see [MCP server](#mcp-server) below.

## Commands

Run the tool:
```
python MailGrab.py
```
or on Windows: `windows.bat` (wraps the same command and pauses on exit).

Install dependencies:
```
python install/install.py
```
or `install/install.bat`. `install/install.py` pip-installs a hardcoded package list (not all of `requirements.txt` — e.g. it skips `bs4`'s pin and several transitive/unrelated deps that live in `requirements.txt`/`install/requirements.txt`). There is a separate root `requirements.txt` used for CodeQL/Renovate dependency tracking; when adding a new import to `MailGrab.py`, add the package to *both* `install/install.py`'s `packages` list and `requirements.txt`.

There are two test files (stdlib `unittest`, no pytest/other framework):
- `test_mailgrab.py` — run with `python test_mailgrab.py`. Exercises the real CLI script end-to-end via `runpy.run_path` against a local `http.server.ThreadingHTTPServer` (no real network needed; `os.system` and the startup `requests.get` connectivity check are mocked out) and asserts on the output files / elapsed time.
- `test_mailgrab_mcp.py` — run with `python test_mailgrab_mcp.py`. Drives the real `mailgrab_mcp_server.py` as a subprocess through the official `mcp` client SDK (`stdio_client` + `ClientSession`) — no hand-rolled JSON-RPC. Each test still spins up its own local mock HTTP server as the crawl target, but MailGrab's own startup connectivity check inside the spawned crawl subprocess is real and unmocked (a real, fast ping/HTTPS request to `oceanofanything.github.io`), so this suite needs actual internet access to pass, unlike `test_mailgrab.py`.

There's still no lint config, and no CI beyond CodeQL scanning (`.github/workflows/codeql-analysis.yml`) and a manual-dispatch PR auto-merge workflow — neither test suite runs automatically on push/PR. Renovate handles dependency bumps (see `renovate.json`).

## Architecture

Everything lives in [MailGrab.py](MailGrab.py) inside `if __name__ == "__main__":` — there are no importable functions/classes outside that block (they're still module-level in effect, since `if` doesn't introduce a Python scope; that's why helper functions defined there can reference `console`/`log`/the CLI-derived config constants as ordinary globals). Two entry points share one crawl/save implementation rather than duplicating it:

1. **Batch mode** (`MAILGRAB()` function): triggered automatically if the file at `--input` (default `_inputUrls.txt`) exists and is non-empty. Reads one URL per line, resolves the crawl depth (CLI `--depth` or an interactive prompt), then loops over each seed URL.
2. **Interactive mode** (bottom of the `__main__` block): runs when the input file is absent/empty. Resolves a single URL and depth (CLI `--url`/`--depth`, or interactive prompts) then crawls once.

Both call the shared `crawlUrls(seedUrl, depth, session, maxWorkers, delaySeconds, timeoutSeconds, sameDomainOnly=, ignoreRobots=, userAgent=, visited=, emails=, emailSources=, socialLinks=, robotsCache=, maxHops=, useSitemap=)`, which BFS-crawls up to `depth` pages total (the historical "depth" is really a total-page-count cap, not a tree-depth limit; `maxHops`/`--max-hops` is the separate, independent link-distance-from-seed cap). Each queued item is a `(url, hopCount)` tuple, not a bare url. `visited`/`emails`/`emailSources`/`socialLinks`/`robotsCache` are mutated in place when passed in — batch mode passes its own accumulators (including `robotsCache`) so state is shared across every seed in `_inputUrls.txt`, not just within one seed's crawl. Per-URL fetch/parse/error-handling logic lives in `_fetchAndExtract()` (one `session.get(url, timeout=...)` call, the same per-exception-type logged/printed handling as before, then email/link extraction from the response). **If you change fetch, error-handling, or link-discovery behavior, it applies to both entry points automatically** — don't duplicate it back into the call sites.

Link discovery in `_fetchAndExtract()` also: resolves `mailto:` hrefs directly into the emails set (skipping `tel:`/`javascript:`/`#`/empty hrefs entirely rather than queuing them), strips URL fragments via `urllib.parse.urldefrag`, drops links whose extension is in `SKIP_EXTENSIONS`, and tags social/contact links (`_isSocialOrContactLink()`, matched against `SOCIAL_DOMAINS`/`CONTACT_PATH_HINTS`) into a separate `socialLinks` set rather than crawling them as pages. Email extraction runs the existing plain regex plus `_findObfuscatedEmails()` (Cloudflare `data-cfemail="<hex>"` XOR-decode, and a `word [at]/at/(at) word [dot]/dot/(dot) word` heuristic regex — the latter can rarely false-positive on prose that happens to contain "at"/"dot"); **both regexes use bounded quantifiers (`{1,64}` etc.), not unbounded `+`** — an unbounded run of word characters with no `@`/`at`/`dot` marker (a base64 blob, minified inline JS) triggered catastrophic (quadratic) regex backtracking that hung the crawl on a single such page, found via adversarial testing. Every collected email is lowercased (case-insensitive dedup — also re-applied when a prior `_results.json` is loaded for `--append`/`--resume`, so a legacy/foreign file can't reintroduce case duplicates) and passed through `_isPlaceholderEmail()` before being returned; a dropped placeholder is reported (`"Filtered N Placeholder Email(s)"`), not silently discarded. `PLACEHOLDER_DOMAINS` is deliberately narrow — only `example.com`/`.org`/`.net` (RFC 2606, can never have real mail) and `wixpress.com` (a site builder's own internal domain) — since domains like `domain.com`/`email.com`/`company.com` are real, live services with real mailboxes; those only match as exact `PLACEHOLDER_EMAILS` addresses. **Don't casually add a domain to `PLACEHOLDER_DOMAINS`** — verify it can never have a real mailbox first, an earlier version wholesale-blocked several real services this way.

`crawlUrls()` applies `--same-domain` scoping (drops discovered links whose netloc differs from the seed's), robots.txt checks (`_isAllowedByRobots()`, which fetches `origin/robots.txt` through the *same* session+timeout — not `RobotFileParser.read()`'s own unbounded fetch — specifically so a slow/unreachable robots.txt can't hang the crawl; a failed fetch is treated as allow-all), and a per-domain rate limit: `effectiveDelay = max(delaySeconds, _crawlDelayFor(...))` waits only if *that domain* was hit recently (tracked in a main-thread-only `lastRequestAt` dict), so a multi-domain crawl doesn't serialize on one shared delay, and robots.txt's own `Crawl-delay` (if larger) always wins. Note: stdlib `RobotFileParser.crawl_delay()` only recognizes an **integer** delay value (`Crawl-delay: 0.3` is silently ignored; `Crawl-delay: 1` works) — a stdlib limitation, not a bug to "fix" here. `--use-sitemap` seeds the initial queue (at hop 1, only if `maxHops` allows it) from `_urlsFromSitemap()` (checks `robots.txt`'s `Sitemap:` line(s) and the default `/sitemap.xml` path) in addition to the seed (hop 0); it's opt-in since it adds extra requests every run. `_urlsFromSitemap()` resolves one level of `<sitemapindex>` (the WordPress/Shopify/most-CMS-default layout — its `<loc>` entries are *other sitemaps*, not pages) into actual page URLs before returning; don't assume every fetched sitemap is a flat `<urlset>`.

`saveResults(scrappedUrls, emails, emailSources, socialLinks, appendMode, verifyMx, timeoutSeconds, maxWorkers)` is the single place both entry points write output — it replaced ~140 lines of duplicated file-writing code, including a pre-existing bug in `MAILGRAB()` where the entire save+report+exit sequence was accidentally nested inside a `for linkList in scrappedUrls:` loop (ran once per scrapped URL instead of once). `appendMode` is `APPEND_RESULTS or RESUME_MODE` at both call sites (resume's output-merging reuses the append code path). If `verifyMx`, `_filterByMX()` runs first (after merging, before writing): one concurrent DNS lookup per *unique domain* (not per email). Only a definitive `dns.resolver.NXDOMAIN`/`NoAnswer` drops the email — any other resolver exception (timeout, no nameservers) is treated as inconclusive and the email is kept (with a console warning), so a flaky DNS lookup can't silently erase a real address. It writes, at the repo root:

- `_emails.txt` / `_scrappedUrls.txt` — the original plain-list-with-banner-header format.
- `_emails.csv` — `email,found_on_url` rows (one row per email/source-url pair).
- `_results.json` — `{"emails": [...], "scrappedUrls": [...], "sources": {email: [urls]}, "socialLinks": [...]}`; this is also the append/resume source of truth (`_loadPriorResults()` reads it back) — `--append`/`MAILGRAB_APPEND=1` unions a prior run's `_results.json` into the new one before writing, and `--resume`/`MAILGRAB_RESUME=1` does the same thing *before* crawling starts (at both call sites), so already-visited pages are skipped during the crawl itself rather than just merged afterward. Resume has no separate persisted frontier/queue file — the seed is always re-fetched regardless of prior visits, since re-walking from it is the only way to discover anything new without one; add real frontier serialization if resuming deep into an interrupted crawl without re-walking any of the graph becomes worth the complexity.
- `_MailGrabLog.txt` — debug-level log via the stdlib `logging` module, filemode `'w'` (truncated every run; note repeated `runpy`-driven runs of the script *within one Python process*, as `test_mailgrab.py` does, make `logging.basicConfig()` a no-op after the first call, so later runs' log files in such a scenario are unreliable to assert on — check console/stdout output instead, see `test_mailgrab.py`'s `KnownLimitationsFixedTest` for the pattern).
- `_inputUrls.txt` (or `--input`'s path) — optional user-supplied seed list that switches the tool into batch mode (unless `--url` is also given, which always wins over an existing seed file).

These `_*.txt`/`.csv`/`.json` files are runtime output; the `.txt` ones are checked into the repo as empty placeholders and get overwritten as a side effect of running the tool.

Most new behavior is configured through `MAILGRAB_*` env vars (`MAILGRAB_MAX_WORKERS`, `MAILGRAB_DELAY`, `MAILGRAB_TIMEOUT`, `MAILGRAB_SAME_DOMAIN`, `MAILGRAB_IGNORE_ROBOTS`, `MAILGRAB_APPEND`, `MAILGRAB_USER_AGENT`, `MAILGRAB_PROXY`, `MAILGRAB_MAX_HOPS`, `MAILGRAB_USE_SITEMAP`, `MAILGRAB_VERIFY_MX`, `MAILGRAB_RESUME`, `MAILGRAB_QUIET`), each of which has a same-named `argparse` CLI flag (`--concurrency`, `--delay`, `--timeout`, `--same-domain`, `--ignore-robots`, `--append`, `--user-agent`, `--proxy`, `--max-hops`, `--use-sitemap`, `--verify-mx`, `--resume`, `--quiet`) that takes priority over the env var. `--config path.json` pre-fills the env vars via `os.environ.setdefault` (so real env vars and CLI flags still win) rather than being a separate config-precedence system — reuse that pattern rather than adding a new one if extending the config surface. `--url`/`--depth` bypass the matching interactive prompt; when either is given, a `NON_INTERACTIVE` flag also skips the final "Press Any Key To Exit" prompt in both entry points (so a fully-flagged run never blocks on stdin), and giving only one of the two without a way to satisfy the other (e.g. `--depth` with no `--url` and no seed file) fails fast with `sys.exit(1)` instead of falling through to a prompt that would hang in a script/CI job.

The shared `session = r.Session()` carries a `User-Agent` header; a validated `PROXY_URL` (`--proxy`/`MAILGRAB_PROXY`, `sys.exit(1)` on an invalid scheme/netloc); and an `HTTPAdapter` with a `urllib3.Retry` (deliberately `connect=0, read=0` — retrying connection/read timeouts would multiply the wait on a hung server and defeat `MAILGRAB_TIMEOUT`; only 5xx status codes are retried, with `backoff_factor` scaled to `REQUEST_TIMEOUT`) sized to `MAILGRAB_MAX_WORKERS`. One known cosmetic quirk from mounting this adapter: a real timeout can still surface as `requests.exceptions.ConnectionError` instead of `Timeout` (urllib3 wraps it in a `MaxRetryError` that `requests` reclassifies) — `_isDisguisedTimeout()` unwraps `ConnectionError.args[0].reason` to detect this and log/print "Timeout Error" correctly anyway. It explicitly excludes `NewConnectionError`/`NameResolutionError` (connection-refused / DNS-lookup-failure) even though both are themselves `ConnectTimeoutError` subclasses in urllib3's actual hierarchy — verified empirically (a dead/typo'd domain raises `NameResolutionError`, a genuine connect timeout raises bare `ConnectTimeoutError`) — since those are real connection failures, not timeouts, and mislabeling them was the single most common real-world way this check went wrong.

Console output uses `rich.console.Console` + `rich.text.Text` for styled status lines (a small set of `sPrimary`/`sWarning`/`sDanger`/`sSuccess`/`sInfo`/`sInput` `Text` objects define the color scheme) and `colorama`/`cursor` for the ASCII banner (`BANNER` class). `--quiet`/`MAILGRAB_QUIET=1` constructs `Console(quiet=True)` (Rich's own flag, suppresses everything printed through it) and instead prints one `printQuietSummary()` JSON line to stdout near the end, for piping into other tools. There's no fake progress-bar animation anymore (it used to only animate the file-save step, never real crawl progress) — `crawlUrls()` prints real `Progress: X/depth Pages Crawled` after each concurrent batch.

At startup the script pings `oceanofanything.github.io` (via `ping`/`curl` depending on `os.name`) as a connectivity check and exits if it fails — this is an external dependency to be aware of when running the tool in a sandboxed/offline environment. `--help` exits before reaching this check.

Both entry points now track a `saveFailed` flag through their final `sys.exit(1 if saveFailed else 0)` — if `saveResults()` raises (a real, if rare, failure mode), the process exits non-zero instead of unconditionally exiting 0, so a caller (a shell script, CI, or the MCP server below) can rely on the exit code alone to know whether output was actually written. That failure message is also printed directly to stderr (not just through the possibly-`--quiet`-suppressed `console`), matching the same pattern already used for the startup validation errors (`--proxy`, out-of-range `--depth`).

## MCP server

[mailgrab_mcp_server.py](mailgrab_mcp_server.py) wraps the crawler as a single MCP tool, `crawl_website`, so MCP-speaking AI agents (Claude Code, Claude Desktop, Cursor, VS Code/Copilot, Codex CLI, ...) can call it directly instead of shelling out to the CLI. Run it with `python mailgrab_mcp_server.py`; see the wiki's MCP Server page for how to point each client at it.

**Design: subprocess, not in-process import.** The tool function doesn't import and call `crawlUrls()`/`saveResults()` in-process — it runs `python MailGrab.py --url ... --depth ... --quiet [...]` as a real subprocess, in a fresh `tempfile.mkdtemp()` per call, then reads that directory's `_results.json` back. Two reasons this is deliberate, not just the easy option:
1. **Stdout isolation.** MCP's stdio transport reserves this process's stdout exclusively for JSON-RPC messages. `MailGrab.py`'s crawl engine prints directly to stdout (via the `rich` console); running it in-process would corrupt the protocol stream mid-crawl. A subprocess has its own stdout/stderr, captured separately via `capture_output=True` — this can't happen by construction, not by discipline.
2. **Output-file isolation.** `MailGrab.py` writes to fixed filenames (`_results.json`, etc.) in the current directory. Concurrent MCP tool calls (a real scenario — nothing stops a client from calling the tool multiple times in parallel) would clobber each other's files if they shared a working directory; a fresh temp `cwd` per call makes that impossible.

**`stdin=subprocess.DEVNULL` is required, not optional.** When `mailgrab_mcp_server.py` itself is launched by a real MCP client, *its own* stdin is the JSON-RPC pipe from that client. Without explicitly redirecting the spawned `MailGrab.py` subprocess's stdin, it inherits that same pipe — which caused real, confirmed ~60-second hangs on every single crawl during development (only reproduced by testing through the actual `mcp` client SDK via a real subprocess launch, not by calling functions in-process — that's exactly the class of bug this design's stdout/stdin isolation exists to prevent, and exactly why `test_mailgrab_mcp.py` drives the server through a real client session rather than importing it).

**The tool's own defaults intentionally differ from the CLI's.** `same_domain` defaults to `True` in the MCP tool (vs. `False` on the CLI) and `depth` defaults to `30` (vs. an interactive prompt) — chosen for safer, more bounded behavior when an AI agent is the one deciding to call this, potentially on a URL it doesn't have full context on. Don't "fix" this to match the CLI's own defaults; it's deliberate.

**Parameter surface is intentionally smaller than the full CLI.** `--append`/`--resume`/`--config` are not exposed — the tool is a stateless, one-shot call per the whole point of running each crawl in its own throwaway temp directory; persisting state across MCP calls would need a different design (e.g. an explicit `work_dir` parameter). Every other CLI flag that makes sense for a one-shot call is exposed 1:1 in `_buildCommand()` — if you add a new CLI flag to `MailGrab.py` that's relevant to a single crawl, add the matching parameter here too and verify the mapping in `_buildCommand()` directly against `MailGrab.py`'s actual `argparse` definitions rather than assuming.

**Errors are raised, not returned.** A failed crawl (bad proxy, out-of-range depth, a subprocess timeout, a missing `_results.json`) raises `RuntimeError` with a message built from the subprocess's `stderr`/`stdout`; FastMCP converts that into an MCP tool error result (`isError: true`) automatically — this is the idiomatic MCP failure pattern, not a `{"error": ...}` dict a caller would have to remember to check for. A crawl that completes but finds zero emails is *not* an error — it returns a normal, empty-ish result.

**The subprocess timeout scales with the caller's own arguments, not just `depth`.** An adversarial security review found the original formula (`min(600, max(60, depth * 2))`) ignored `concurrency`/`timeout` entirely, so a deliberately polite crawl (low `concurrency`, high per-request `timeout`) could get killed well before it legitimately finished. `_computeSubprocessTimeout(depth, concurrency, timeout)` fixes this: `ceil(depth / concurrency) * (timeout + 5) + 30`, clamped to `[60, 1800]`. It's extracted as a standalone function specifically so `test_mailgrab_mcp.py`'s `SubprocessTimeoutFormulaTest` can check the formula directly, instead of needing a real 75+ second crawl to catch a regression.

**A clean exit with no `_results.json` is retried once, automatically.** Confirmed as a rare (~1-3%), non-deterministic race in `MailGrab.py`'s own pre-existing startup connectivity check under heavy concurrent process-launch load — not a new bug introduced by the MCP server, and not worth touching that well-tested code for. `crawl_website()` retries the same (still-empty) `workDir` once before treating it as a real failure.
